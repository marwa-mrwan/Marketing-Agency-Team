# الاستعادة المشروطة واختبار القبول

## قرار الاستعادة

| حالة المضيف | التصرف |
|---|---|
| الحزم موجودة ومحرك متوافق لكن Agent Teams غير مفعّلة | افحص Plugins/experimental bundle وفعّل Agent Teams بإذن المستخدم؛ أعد تحميل الواجهة وافتح جلسة جديدة. لا يلزم نسخ الكود غالبًا. |
| الحزم الأربع محذوفة فقط، ومحرك DSH وbase وواجهات العميل ما زالت متوافقة | يستطيع مطور استخدام الحزم المحفوظة في بيئة اختبار منفصلة وتركيب layer التفعيل بعد base، ثم اختبار القبول كاملًا. وجود نفس رقم الإصدار وحده لا يكفي. |
| أزيلت خدمات subagents/session/projection أو تغيرت واجهاتها أو row ids | لا تنسخ ملفات فوق التطبيق الجديد. يلزم نقل للكود أو runtime مستقل متوافق أو استعادة إصدار التطبيق القديم الكامل. هذه الحزمة وحدها لا تحقق ذلك. |
| المضيف ليس DSH/ZadLoop | الحزم ليست MCP ولا Agents عامة؛ لن تضيف أدوات للمضيف بمجرد تنزيلها. |

## قبل أي تغيير

1. سجل إصدار التطبيق والمنصة وهوية build والـprofile المقصود. شغّل فحص الحزمة ثم المقارنة الاختيارية؛ لا تشارك logs أو profiles خامًا على GitHub.
2. احفظ installer موثوقًا كاملًا لنفس المنصة وبصمته، ونسخة خاصة قابلة للاستعادة من إعداداتك وجلساتك خارج المستودع العام. توقف عن استخدام أي مجلد جلسات ستنسخه حتى لا تحصل على snapshot غير متسق. لا تنقل cookies أو tokens في هذه الحزمة.
3. اختبر في مستخدم نظام/VM وworkspace تجريبيين، بعيدًا عن حسابات العملاء. لا تشغّل إصدارين على نفس مخزن الجلسات؛ قد تكون migrations أحادية الاتجاه.
4. لا تتجاوز توقيع Electron أو تحقق client-set ولا تعدّل `app.asar` أو ملفات البرنامج مباشرة. حزمة UI قد تحتاج إعادة بناء client-set متوافقة؛ نسخ ملفاتها لا يسجلها في الواجهة.

## تركيب بواسطة مطور — ليس installer تلقائيًا

أرشيفات snapshots تحفظ ملفات التطبيق دون تعديل ومعها LICENSE المسترجع من npm. `package.json` المحلي يحتوي `workspace:*` و`workspace:~`؛ **لا تنفّذ `npm install` على الحزم المنسوخة وتتوقع نجاحه**. يجب إعداد workspace متوافق أو تحويل ranges إلى إصدارات محققة مع lockfile ومراجعة التغييرات. سجل dependency_inventory يرصد manifests فقط ولا يحتوي كل كود dependencies، ولا يمثل SBOM/lockfile كاملًا؛ unresolved_dependencies يجب حلها من lockfile/توزيع موثوق.

حزمة profile تحتوي `cordis.patch.yml`. يوضح patch تعطيل أدوات subagent القديمة المتعارضة وإضافة خدمة Team والأدوات وUI بعد `dsh-base`. أسماء `spawn` و`fork` مزودا إنشاء داخليان، وليسا اسمي مزودي LLM. راجع وثائق الحزمة داخل الأرشيف قبل التركيب.

في توزيع DSH CLI متوافق ومهيأ بالفعل، تصف وثائق المصدر هذا الأمر:

```bash
dsh plugin --profile headless add @deepseek-ai/dsh-experimental-agent-team-profile
```

هذا مثال upstream **ليس أمر استعادة offline مثبتًا لهذه النسخة**: الأمر غير مثبت الإصدار وقد يجلب إصدارًا مختلفًا، ويعدل profile، ويحتاج مراجعة واعتمادًا منفصلًا قبل تنفيذه. لا تشغّله على production أو تستبدل به النسخة المحلية المختلفة عن npm. لا نضع أمر تركيب تلقائي مضللًا.

## اختبار القبول المطلوب قبل الادعاء بالنجاح

- تظهر الأدوات التسع في جلسة جديدة، لا مجرد أسماء في prompt. الواجهة تعرض roster وtask board إذا كان الهدف Desktop/Web.
- يظل Lead على موديل الجلسة. قبل إنشاء المتخصص التجريبي يختار المستخدم Agent/model أو يوافق صراحة على قيد الأداة؛ schema المحفوظ لا يتيح model لكل استدعاء.
- بأذن المستخدم في تكلفة الموديل: أنشئ عضوًا تجريبيًا، تحقق من `list_agents`، أرسل مهمة نصية اصطناعية، واجمع رده. لا تعتبر `send_message` نجاح معالجة.
- أنشئ مهمتين ببيانات مصطنعة وdependency وwrite_scopes؛ تحقق من عدم جاهزية التابعة، claim بأحدث revision، رفض revision قديم، complete ثم جاهزية التابعة.
- اختبر `wait_agent` مع عضو يعمل، وحالة `noProgress` عند عدم وجود عضو منتج، واختبر interrupt لمهمة تجريبية دون فقد inbox.
- أغلق runtime الاختباري بصورة سليمة وأعد تشغيله، ثم تحقق من roster/tasks ومراسلة عضو inactive بدون إنشاء نسخة مكررة. افحص استمرار الواجهة والتنقل بين المحادثات.
- اختبار الاستقلال يحتاج تشغيل العملية من ملفات النسخة وحدها دون الرجوع إلى تثبيت ZadLoop الأصلي أو `node_modules` الخاصة به. لم يُنفذ هذا الاختبار ولم تنجح الحزمة فيه بمجرد اجتياز hashes.

## الرجوع

أغلق runtime الاختباري؛ ارجع لنسخة installer/الـprofile الخاصة السابقة في بيئة منفصلة. لا تعمل downgrade فوق مخزن جلسات عدله إصدار أحدث. لا تحذف ملفات مستخدم أو تفك حزم فوق التطبيق الحالي. لا تستعد credentials من GitHub.

## سجل الاختبارات

[doctor.py](<doctor.py>) يفحص hashes ومسارات الأرشيفات، الملفات المنتظمة، عدم وجود symlinks داخل الأرشيفات، ووجود declarations الأدوات التسع. المقارنة تفحص هوية build وملفات الحزم وmanifests التبعيات المتاحة محليًا. هذه فحوص ساكنة، ليست integration أو إثبات استقلال أو مراجعة أمنية شاملة. راجع [EVIDENCE.md](<EVIDENCE.md>) لنتائج التنفيذ الفعلية وما لم يُختبر.
